Claude Skills · Deep dive

Skills: what they are,
where to get them, how to write your own.

Skills are reusable behaviour modules for Claude Code and Claude.ai. Drop a markdown file into the right folder and Claude gains a new capability — security review, PR descriptions, brand-voice writing, image generation workflows. This page covers everything: installing official skills, downloading from the community, authoring your own, and a starter library you can grab right now.

The shortest possible explanation. A skill is a markdown file that tells Claude how to do a specific task. When you ask Claude to do that task, it reads the file and follows the instructions. That's it — no install scripts, no compilation, no API. Just a .md file in a known folder.
Concept

What a skill actually is, under the hood

The structure

A skill is a folder with at least one file: SKILL.md (or any .md file with YAML front-matter). Optional: supporting scripts, reference data, sub-prompts.

my-skill/
├── SKILL.md           ← required: instructions + metadata
├── examples/          ← optional: example inputs/outputs
└── helpers/           ← optional: scripts the skill can call

The minimum SKILL.md

---
name: pr-description
description: Generate a clear pull request description from staged changes.
---

When the user asks for a PR description:
1. Run `git log main..HEAD --oneline` to list commits.
2. Run `git diff main..HEAD --stat` to see scope.
3. Output: ## Summary (1-3 bullets), ## Test plan (checklist), ## Notes for reviewer (anything non-obvious).
4. Keep under 200 words.

How Claude uses it

  1. Claude reads all SKILL.md files in the configured skill folders on startup.
  2. It sees the description field of each.
  3. When your message matches a skill's purpose, Claude follows that skill's instructions.
  4. If multiple skills could apply, Claude picks the best fit — or asks you to clarify.
Skills vs MCP servers vs Subagents — what's the difference?
  • Skills = instructions ("how to do X") — markdown only, no code.
  • MCP servers = new tools ("can do Y") — actual code/services Claude calls.
  • Subagents = a separate Claude instance that does a sub-task in parallel — for keeping the main context clean.
Install paths

Where skills live on disk

LocationScopeWhen to use
~/.claude/skills/User (all projects)Skills you want available everywhere — your writing voice, code review style, commit messages.
./.claude/skills/Project (this folder only)Skills specific to one project — the project's tests, deployment, domain rules.
Built-in (in the Claude Code package)Bundled defaultsYou don't manage these — they ship with Claude Code.

On Windows, replace ~/ with %USERPROFILE%\. Folder structure is the same.

Quick install: just drop a file in

# Mac/Linux
mkdir -p ~/.claude/skills/commit-message
nano ~/.claude/skills/commit-message/SKILL.md
# Paste skill content, save

# Windows (PowerShell)
mkdir $env:USERPROFILE\.claude\skills\commit-message
notepad $env:USERPROFILE\.claude\skills\commit-message\SKILL.md

No install command needed. Next session, Claude sees the new skill.

How to install a skill from GitHub (fastest)

# Clone the whole repo to a temp spot
git clone https://github.com/[user]/[repo].git /tmp/skills-source

# Copy just the skills you want
cp -r /tmp/skills-source/skills/security-review ~/.claude/skills/

# Or for a single SKILL.md file
mkdir -p ~/.claude/skills/security-review
curl -o ~/.claude/skills/security-review/SKILL.md \
  https://raw.githubusercontent.com/[user]/[repo]/main/skills/security-review/SKILL.md

Starter library

8 skills to copy into ~/.claude/skills/ right now

Each one is a complete SKILL.md. Copy → paste into a new file → done.

1. commit-message/SKILL.md

---
name: commit-message
description: Write a clear conventional commit message based on staged changes
---

When the user asks for a commit message:
1. Run `git diff --cached` to see staged changes (and `git status` if context is unclear).
2. Identify the type: feat / fix / chore / docs / refactor / test / perf / style.
3. Subject line: imperative mood, ≤50 chars, no period. ("add" not "added")
4. If non-trivial, add a body separated by blank line. Explain WHY, not WHAT.
5. Reference any issue: "Closes #123" at the bottom.

Never:
- Use emojis unless CONTRIBUTING.md asks for them
- Mention Claude / AI in the message
- Write "as per the user's request" or similar fluff

2. pr-description/SKILL.md

---
name: pr-description
description: Generate a pull request description from the diff against main
---

When asked for a PR description:
1. Run `git log $(git merge-base HEAD main)..HEAD --oneline` for commits.
2. Run `git diff $(git merge-base HEAD main)..HEAD --stat` for scope.

Output exactly this structure:

## Summary
[1-3 bullets — what changed and why]

## Test plan
- [ ] [step 1]
- [ ] [step 2]

## Notes for reviewer
[Anything non-obvious. Tradeoffs taken. Things considered & rejected.]

Keep total under 250 words. Reviewers don't read more.

3. security-review/SKILL.md

---
name: security-review
description: Audit a file or PR for common security issues
---

When asked for a security review of a file or change:

1. Look for these specific issues, in priority order:
   - Hardcoded secrets (API keys, passwords, tokens) — even in examples
   - SQL injection (string concat in queries, unparameterized inputs)
   - XSS (innerHTML with user input, dangerouslySetInnerHTML in React)
   - SSRF (user-controlled URLs in fetch/axios calls)
   - Path traversal (user input in file paths without sanitization)
   - Auth bypass (missing auth checks on routes, weak session handling)
   - Insecure deserialization (eval, pickle, unsafe yaml.load)
   - CORS misconfiguration (Access-Control-Allow-Origin: *)

2. For each finding:
   - file:line
   - severity: critical / high / medium / low
   - the issue (1 sentence)
   - the fix (code snippet)

3. If clean, say so explicitly. Don't invent issues.

Skip: style nits, theoretical risks that can't actually happen in this code path.

4. simplify/SKILL.md

---
name: simplify
description: Review changed code for over-engineering and simplify it
---

When asked to simplify recently changed code:

1. Run `git diff` to see what changed.
2. For each change, check for:
   - Premature abstraction (single-use helpers, classes wrapping one function)
   - Unnecessary error handling (catching things that can't happen)
   - Defensive programming for internal callers
   - Backwards-compat shims for code we control
   - Duplication that could be extracted (only if used 3+ times)
   - Dead code / unused params / orphan imports
   - Comments restating what the code does

3. For each, propose a smaller version. Show before/after diffs.

Default to fewer lines, fewer abstractions, fewer features. Three similar lines beats a premature abstraction.

5. brand-writer/SKILL.md

---
name: brand-writer
description: Write copy in [BRAND] voice for any deliverable
---

You are writing for [BRAND NAME].

## Voice rules
- UK English. No corporate-speak ("circle back", "leverage", "moving forward").
- Confident, never hedging. Cut "just", "maybe", "I think", "perhaps".
- One strong sentence beats three soft ones.
- Use contractions: it's, don't, we're.
- Never start with "In today's fast-paced world…" or similar throat-clearing.

## Audience
[Describe target audience demographics + psychographics]

## What we sell
[Products + the actual value they create]

## Examples of past copy that nailed the voice
[Paste 2-3 short examples here so the model can pattern-match]

When asked to write something:
1. Ask which deliverable + word count if not given.
2. Draft v1.
3. Cut 30%. Show v2.
4. Briefly explain (3 bullets max) what changed and why.

6. plan-then-do/SKILL.md

---
name: plan-then-do
description: For non-trivial tasks, plan before executing
---

For any task that involves more than 3 steps OR touches more than 1 file:

1. **Plan** (3-5 bullets): what files you'll change, in what order, why.
2. **Clarify** (max 3 questions, only if genuinely ambiguous): wait for user reply.
3. **Execute**: do the work.
4. **Verify**: run tests / linter / build. Report results.

Skip the plan step for trivial tasks (typo fix, single-line change, rename).

Never silently change scope. If you discover the task is bigger than expected, stop and ask.

7. devil-advocate/SKILL.md

---
name: devil-advocate
description: Stress-test a plan, idea, or decision before committing
---

When asked to be devil's advocate on a plan, idea, decision, or piece of code:

Output exactly:

## 5 strongest counter-arguments (ranked by likelihood × impact)
1. [argument] — Likelihood: H/M/L · Impact: H/M/L
2. ...

## Cheapest test for each (1-3 days, low cost)
[How would you test each before committing?]

## Kill criteria
[What evidence would make me abandon this entirely?]

## Steel-man (one sentence)
[The strongest reason this WILL work — to keep you honest]

Be direct. Don't soften. The kindest thing is to save them from a bad decision.

8. fewer-permission-prompts/SKILL.md

---
name: fewer-permission-prompts
description: Add a curated allowlist of safe commands to settings.json to reduce prompts
---

When invoked:

1. Read the recent session transcript (or ask the user to paste it).
2. Identify all Bash and MCP tool calls that are clearly read-only and safe:
   - git status, git log, git diff, git branch, git show
   - ls, cat, head, tail, wc, find (read-only)
   - grep, rg, fd
   - npm list, pnpm list, pip list (read-only)
   - any "show / read / get / list" MCP tool calls

3. Generate a JSON snippet to add to ~/.claude/settings.json:

{
  "autoApprove": [
    "Bash(git status)",
    "Bash(git log)",
    ...
  ]
}

4. NEVER add destructive commands: rm, push, force, reset --hard, drop, delete.
5. Show the diff for the user to apply manually.
Authoring

Write your own skill in 5 minutes

The recipe

  1. Identify a task you do repeatedly with Claude (e.g. "write release notes from recent commits").
  2. Open the chat where you've successfully done it 2-3 times.
  3. Distill the instructions you'd give a junior to do it: inputs, steps, output format, constraints.
  4. Save as ~/.claude/skills/[skill-name]/SKILL.md with YAML front-matter.
  5. Test in a new session — ask Claude to do the task. Iterate the SKILL.md until output is consistent.

The good-skill checklist

  • ✅ Single purpose. One skill per task. Don't bundle.
  • ✅ Description is searchable. The model picks skills from descriptions — make them concrete.
  • ✅ Numbered steps. Models follow numbered steps better than prose.
  • ✅ Output format spelled out. Show the exact structure you want.
  • ✅ "Never do" list. Saves you from re-correcting common mistakes.
  • ❌ Don't paste your CLAUDE.md content into a skill. CLAUDE.md is for project-wide rules; skills are for specific tasks.

Sharing your skills

  • Put them in a public GitHub repo named your-name-claude-skills with a clear README.
  • Tag the repo with claude-skills so it shows up in searches.
  • Submit to awesome-claude-code via PR.
  • Post in r/ClaudeAI and the Anthropic Discord #claude-code channel.
